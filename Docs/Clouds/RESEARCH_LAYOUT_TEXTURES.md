## 1. Вопрос 1 — в каком пространстве и в какой момент читается каждая текстура

### 1.1. Пространство: вертикаль сферическая, горизонталь плоская. Это ДВА разных пространства

**[ИСХ]** `Engine/Shaders/Private/VolumetricCloudMaterialPixelCommon.ush`:

```
50:  MaterialParameters.AbsoluteWorldPosition = DFFastSubtract(TranslatedWorldPosition, InputView.PreViewTranslation);
60:  float3 AbsoluteWorldPositionTruncated = TranslatedWorldPosition - DFHackToFloat(InputView.PreViewTranslation);
61:  float CloudSampleAltitude = length(AbsoluteWorldPositionTruncated - CloudLayerParams.CloudLayerCenter);
62:  MaterialParameters.CloudSampleAltitude        = CloudSampleAltitude - CloudLayerParams.PlanetRadius;
63:  MaterialParameters.CloudSampleAltitudeInLayer = CloudSampleAltitude - CloudLayerParams.BottomRadius;
64:  MaterialParameters.CloudSampleNormAltitudeInLayer = saturate(MaterialParameters.CloudSampleAltitudeInLayer * CloudLayerParams.ToNormAltitude);
```

с `ToNormAltitude = 1.0 / (TopRadius - BottomRadius)` (строка 34) и всеми радиусами в сантиметрах
(строки 30–33, `KILOMETER_TO_CENTIMETER`).

- **Ось высоты — РАДИАЛЬНАЯ**: расстояние до центра слоя минус нижний радиус, нормированное толщиной
  оболочки. Это доля между двумя концентрическими сферами, а не высота над плоскостью.
- **Горизонтали движок не даёт вообще.** Материал получает **абсолютную мировую позицию в сантиметрах**
  (строки 50–51) и больше ничего: ни UV слоя, ни сферических координат, ни проекции. Никакого
  «сферического проложения» в движке не существует.

**[ГРАФ✓]** Сам граф берёт из этой позиции **плоскую проекцию XY** и делит её на
`Layout_CloudGlobalScale` — **`DefaultValue=256.000000`, и `Desc` параметра говорит «in km»** (L999,
L1004) — поворачивает вокруг Z **свободным углом** (`MaterialExpressionRotator_1`, узел 187, L4269) и
вычитает смещение (`Subtract`, узел 185, L4217). Каналы смещения названы буквально `Position.X/Y/Z` и
`SkyTextureRotation` (L4236). Перепроверено, §8.4.

**Ответ на вопрос дословно: плоское мировое проложение по XY с периодом 256 км, ось высоты — сферическая
доля слоя.** Кривизна планеты входит только в высоту; где облако — решается по плоской карте, как если бы
планета была плоской. На 256 км это ошибка порядка `256²/(8·6371) ≈ 1.3` км высоты на краю тайла, и Epic
её просто не учитывает.

Три текстуры адресуются НЕ одинаково — **[ГРАФ✓]** для профиля и паттерна (§8.1), **[ГРАФ]** для маски:

| текстура | координата | что это |
|---|---|---|
| `Layout_CloudGlobalPattern` | `(SkyTexScale.xy − 0.5) · Layout_CloudPerTypeScale[i]` | плоская мировая XY, **свой масштаб у каждого вида** |
| `Layout_CloudHeightProfile` | `(NormAltitudeInLayer, L_i)` | **это вообще не мировая координата** — U высота, V значение паттерна |
| `Layout_GlobalCloudMask` | `(SkyTexScale + Layout_GlobalTexturePlacement.rgb).xy` | плоская мировая XY, **смещение паттерна прибавлено обратно** — маска привязана к миру и не ездит вместе с паттерном |

Последняя строка — единственная содержательная асимметрия координат, и она намеренная: паттерн можно
двигать и вращать, маска остаётся на месте.

### 1.2. Момент: не «раз на шаг марша», а раз на КАЖДОЕ вычисление материала

**[ИСХ]** `Engine/Shaders/Private/VolumetricCloud.usf`, основной цикл:

```
858:  UpdateMaterialCloudParam(MaterialParameters, SampleTranslatedWorldPosition, …, CloudLayerParams, TRACING_SHADOW_DISTANCE_OFF, …);
861:  if (MaterialParameters.VolumeSampleConservativeDensity.x <= 0.0f) { … continue; }   // пропуск пустоты
892:  if (MaterialParameters.CloudSampleNormAltitudeInLayer <= 0.0f || … >= 1.0f) { t += StepT; continue; }
903:  VolumetricCloudCalcPixelMaterialInputs(MaterialParameters, PixelMaterialInputs);
905:  const MATVEC ExtinctionCoefficients = ColorToMATVEC(SampleExtinctionCoefficients(PixelMaterialInputs));
```

То есть на каждом шаге материал вычисляется **дважды и по-разному**:

1. `UpdateMaterialCloudParam` считает **только выход №6** — консервативную плотность
   (`VolumetricCloudMaterialPixelCommon.ush:68-70`, `GetVolumetricAdvancedMaterialOutput6`, под гардом
   `MATERIAL_VOLUMETRIC_ADVANCED_CONSERVATIVE_DENSITY`; без него подставляется 1.0, строки 66–67, с
   комментарием «medium is potentially present in case it is not fed by the user»).
2. Полный материал — строка 903, и только если сэмпл пережил обе отбраковки.

**[ИСХ] И на каждом шаге ТЕНЕВОГО луча — тоже.** `UpdateMaterialCloudParam` вызывается ещё в семи местах:
строки **991, 1012** (тень «вниз» / к земле), **1092, 1106** (первый источник), **1181** (второй),
**1317** (интегратор объёмной тени), **1920** (проход теневой карты облаков), **2186** (марш к свету), — и
за каждым из них следует `VolumetricCloudCalcPixelMaterialInputs` (999, 1019, …). Число вычислений
материала за кадр на порядок больше числа шагов основного марша.

**Это и есть цена вопроса.** У UE три текстуры раскладки читаются внутри самого горячего цикла кадра, по
разу на каждое вычисление материала, включая теневые лучи. Плюс к этому — том шума, три октавы. Epic
платит это, потому что у него нет предвычисленного поля вообще: материал и есть поле.

### 1.3. Что движок читает обратно

**[ИСХ]** Из четвёрки консервативной плотности движок читает **только `.x`** —
`VolumetricCloud.usf:861, 994, 1111, 1185, 2190`, всюду `VolumeSampleConservativeDensity.x <= 0.0f`.
Остальные три канала движку не нужны и им не используются.

**[ГРАФ]** `ShapeModel.md` §0 утверждает, что материал читает эту же четвёрку **сам у себя** обратно через
`VolumetricAdvancedMaterialInput` и собирает extinction из каналов `.g/.b/.a`, то есть четыре канала — это
четыре промежуточные величины (консервативная плотность, вес паттерна, профиль−0.5, шум), а не четыре
вида. Проверить это по исходникам нельзя; узел `VolumetricAdvancedMaterialInput` в движке существует
(поиск по `CloudSampleNormAltitudeInLayer` показывает работающий механизм атрибутов), но содержимое графа
— нет.

## 2. Вопрос 2 — что означает «канал = вид» в `Layout_CloudHeightProfile`

**Ответ: третье. Это ни веса смешения, ни выбор одного вида — это четыре НЕЗАВИСИМЫХ поля, объединяемых
`max` в самом конце.**

**[ДОК]** Дословно, `UEReference/Documentation/EpicDoc_CloudMaterial.md` §2 (публичная страница Epic
*Volumetric Cloud Material in Unreal Engine*):

> «This texture describes the shape of the clouds as the altitude changes. Each channel of this texture
> describes the profile shape **and relative altitude** of a different cloud type».

и та же раскладка каналов повторяется в трёх текстурах: R Stratocumulus, G Altostratus, B Cirrostratus,
A Nimbostratus.

**[ГРАФ✓]** Механика, перепроверена по узлам (§8.1). Для вида `i ∈ {r,g,b,a}`:

```
uv_i = (SkyTexScale.xy − 0.5) · Layout_CloudPerTypeScale[i]
L_i  = Pattern.Sample( uv_i )[i]                                  // «есть ли здесь этот вид»
P_i  = Profile.SampleLevel( float2(NormAltitudeInLayer, L_i), 0 )[i]   // «какой он здесь формы»
```

Три следствия, и все три содержательные:

1. **Ось V профиля — не мир и не время, а значение паттерна размещения В ЭТОЙ ЖЕ ТОЧКЕ.** Профиль вида —
   это семейство кривых `f(высота, покрытие)`, а не кривая. У края пятна вид низкий и плоский, в центре
   того же пятна — башня, и это **одна текстура без единого дополнительного параметра**.
2. **Значение паттерна используется дважды и по-разному**: как V-координата профиля (какой формы) и как
   внешний множитель всей суммы (есть ли вообще).
3. **Выборка профиля принудительно с мипа 0.** Мипы запрещены: иначе вдали кривые разных покрытий
   смешиваются между собой и вид теряет форму.

### 2.1. «У нас девять видов, а каналов четыре» — прямого соответствия и не требуется

Расхождения здесь нет, и это стоит сказать явно, потому что оно выглядит расхождением.

- У UE **четыре — это ширина текселя**, потолок структурный.
- У нас **тоже четыре в одном небе**: `CLOUD_SPECIES_SLOTS 4`, `Editor/Resources/Shaders/Common/CloudField.glslh:59`,
  и комментарий там ссылается ровно на эту причину. Девять — это **библиотека на диске**
  (`.decloudtype`), а не то, что одновременно в кадре. Это уже записано в `PLAN_CLOUD_TYPES.md` §3а.
- Значит **канал текстуры раскладки соответствует СЛОТУ СЛОЯ, а не роду облака.** Канал R — это «первый
  вид этого неба», каким бы он ни был, а не «стратокумулюс». У UE это совпадает, потому что его четыре
  слота зафиксированы навсегда; у нас — нет, и это преимущество, а не проблема.

### 2.2. Одно расхождение, которое надо назвать: четвёртый канал у UE неравноправен

**[ГРАФ✓]** Три первых вида объединяются `max` (узлы 89/90 и 91/92), а четвёртый (Nimbostratus) входит
**через `lerp` по скаляру `StormClouds`** (узел 126, альфа — узел 127, L2887) — то есть буря у Epic не
пятый участник максимума, а глобальное переключение режима. `Layout_CloudType` по умолчанию
**(1, 1, 1, 2)** (L2068), то есть штормовой вид ещё и удвоен, а `StormClouds` по умолчанию 0.
**Поправка к `ShapeModel.md`: четвёртый вид исключается из максимума СТРУКТУРНО**, маской RGB на
умножении (L2124, L2106), а не отдельной цепочкой — подробности в §8.2.

У нас все четыре слота равноправны (`CloudField.glslh:274-287`, цикл `max` по слотам). Переносить
асимметрию Epic не предлагается: у нас нет сущности «буря», и её появление — отдельное решение
(`PLAN_WEATHER.md`, D-16/D-18), а не побочный эффект раскладки.

### 2.3. Как «канал = вид» ложится на НАШУ модель формы

Это ключ ко всему разбору, и он не очевиден, потому что наша форма устроена иначе.

У UE вертикальная форма — **таблица**, потому что поле размещения двумерно и вертикали в нём нет вовсе.
У нас поле формы **трёхмерно по построению**: профиль — нормированное поле расстояний до объединения
сглаженных объёмных сгустков (`Engine/Assets/CloudProceduralVolume.hpp`, §Э5). Вертикальную форму задаёт
**геометрия сгустка** — его высота над землёй, три радиуса, скос стопки, наковальня, — а не кривая.

И, что важно, **зависимость «форма от покрытия» у нас УЖЕ ЕСТЬ и работает ровно как у UE**:
`CloudProceduralVolume.cpp:700-713` вычисляет `fill` — насколько глубоко клетка внутри порога — и
комментарий там прямо говорит:

> «EDGE TOP FRACTION IS WHAT A SHALLOW CLUSTER LOSES. The type says how tall it is where the patch has only
> just begun, and `fill` is how far inside the patch this cell is — so a rim cell is low and flat and a core
> cell is a tower. **That is decision D-13's whole intent, carried by the placement instead of by a second
> axis of a table.**»

То есть `fill` — это **в точности ось V текстуры профиля UE**, реализованная геометрией вместо таблицы.
Это не совпадение и не натяжка: это одна и та же семантика, и она уже куплена.

**Отсюда прямой вывод для проектирования: нарисованный `Layout_CloudGlobalPattern` — это вход в `fill`
и в порог живости клетки, а `Layout_CloudHeightProfile` — это НЕ третья текстура, которую надо где-то
читать, а вопрос «оставляем ли мы вертикальную форму геометрии сгустка или отдаём её нарисованной
кривой».** Он разбирается отдельно, в разборе устройства, а не здесь.

## 3. Вопрос 3 — как `GlobalCloudMask` взаимодействует с покрытием

**Ответ: складывается. Ни умножения, ни ремапа нет ни в одном месте.**

**[ДОК]** `LayoutParameters.md`, дословно с публичной страницы Epic:

> `Layout_GlobalCloudMask` — «Adds clouds to or removes clouds from the global pattern texture in the
> masked region», per type.
> `Layout_GlobalCoverage` — «Overall cloud cover; **positive adds, negative removes**».

То есть даже документация для художника называет обе величины аддитивными, а не множителями.

**[ГРАФ✓]** Точное место и порядок, перепроверено по узлам (§8.3):

```
maskTerm = dot( Layout_CloudTypeMask.rgb, M · Layout_CloudType.rgb ) · ( Layout_CloudTypeMask.a · 0.01 )

shape    = layout · ( (profile − 0.5) + (noise − bias + coverage) · strength )
sum      = maskTerm + shape                        // узел с авторским комментарием "Add additive mask"
density  = sum · Cloud_GlobalDensity
```

Разбор по существу:

- **Маска стоит СНАРУЖИ и ПОСЛЕ всего.** Она не входит ни в профиль, ни в шум, ни в поле размещения —
  она складывается с уже собранной формой. Убавлять она умеет за счёт **отрицательных значений
  `Layout_CloudTypeMask`**, а не за счёт умножения на что-то меньше единицы.
- **Покрытие — тоже биас, но в другом месте**: внутри шумового члена, до сложения с профилем, **без
  клампа**. Дефолт `Cloud_GlobalCoverage` = −0.2.
- **Единственный множитель во всей композиции — двумерное поле размещения**, и он снаружи суммы.
- Смещение профиля на **−0.5** делает его знакопеременным: где профиль ниже половины, он вычитает из
  шума, то есть работает как порог, а не как огибающая.
- **По умолчанию маска даёт ровно ноль**: `Layout_CloudTypeMask = (0,0,0,1)`, а вклад ещё и давится на
  0.01. То есть в штатном небе UE **маска не делает ничего**, и пустой слот у эталона бесплатен — ровно
  то требование, которое тимлид ставит нам.

**Что это значит для нас.** У нас покрытие — `smoothstep`-порог, сохранённый вопреки эталону решением
**D-15** с названным несущим входом (измеренный дефект вуали). Сегодня, после §Э5 и §RW, порога в прежнем
виде уже нет: `Coverage` адресует **долю неба напрямую** через долю живых клеток
(`CloudProceduralVolume.cpp:685-691`), с измеренным отображением `pow(cellCoverage, 0.68)` и калиброванной
поправкой на упаковку. Это **третья конструкция**, не UE-шная и не прежняя наша, и она откалибрована
числами (§RW: промах не более 0.019 на пяти настройках). Переносить аддитивный биас Epic поверх неё нельзя
без пересмотра D-20, потому что это переавторизует каждую сцену.

**Вывод: маска у нас обязана войти как модулятор `cellCoverage` в той же точке, где сегодня стоит
`PatchField`, а не как аддитивный член после сборки формы.** Точка одна, она уже существует, и
отображение «слайдер → доля неба» вокруг неё уже откалибровано.

## 4. Вопрос 4 — есть ли у UE понятие «пятна погоды»

**Ответ: НЕТ. И в отличие от вопросов 1–3, этот проверяется по исходникам, а не по графу.**

**[ИСХ]** `Engine/Source/Runtime/Engine/Classes/Components/VolumetricCloudComponent.h` — весь набор полей
компонента:

| категория | поля |
|---|---|
| `Layer` | `LayerBottomAltitude` (36), `LayerHeight` (40), `TracingStartMaxDistance` (44), `TracingStartDistanceFromCamera` (48), `TracingMaxDistanceMode` (52), `TracingMaxDistance` (56) |
| `Planet` | `PlanetRadius` (60), `GroundAlbedo` (66) |
| `Cloud Material` | **`Material`** — `TSoftObjectPtr<UMaterialInterface>` (71) |
| `Cloud Tracing` | `bUsePerSampleAtmosphericLightTransmittance` (75), `SkyLightCloudBottomOcclusion` (81), четыре `*SampleCountScale` (88–115), `ShadowTracingDistance` (121), `StopTracingTransmittanceThreshold` (127) |
| `Art Direction` | четыре `AerialPespective*` (131–140) |

**Ни одного поля про покрытие, размещение, погоду, ветер или форму.** Всё это делегировано материалу
одним указателем (строка 71). То есть у UE «пятно погоды» не существует не потому, что его решили не
делать, — а потому, что у компонента вообще нет поверхности, на которой оно могло бы жить.

**[ГРАФ]** Внутри материала ближайшее к «пятну» — это сама текстура размещения плюс маска, то есть
**нарисованные данные**. `ShapeModel.md` §13 отдельно перечисляет, чего в графе искали и не нашли, и
процедурного крупномасштабного модулятора покрытия там нет ни в каком виде: нет второго поля, нет
низкочастотной октавы, работающей на покрытие, нет зависимости формы от расстояния кроме `Fade Near
Camera`.

**У нас такое пятно есть, и оно процедурное.** `CloudProceduralFieldParams::PatchTileKm` (21 км) и
`PatchStrength` (0.60), §RW. Применяется в `CloudProceduralVolume.cpp:662-674`:

```cpp
float cellCoverage = std::clamp( params.Coverage, 0.0f, 1.0f );
if ( patchStrength > 1e-4f )
{
    const float patch = PatchField( patchSeed, centre, params.PatchTileKm );
    cellCoverage = std::clamp( cellCoverage * ( 1.0f + patchStrength * ( 2.0f * patch - 1.0f ) ), 0.0f, 1.0f );
}
```

с комментарием, который стоит процитировать целиком, потому что он и есть определение задачи:

> «WHERE THE WEATHER IS BUSY AND WHERE IT IS CLEAR. The patch field is sampled at the CELL's own site rather
> than per voxel, so it **modulates whole clouds into and out of existence instead of eroding their edges**
> — which is what a weather system does and what erosion does not. **It is symmetric about the slider, so it
> moves cloud around the sky rather than adding it**.»

> ⚠️ **Это ровно то, что делает `Layout_GlobalCloudMask`, только процедурно вместо нарисованного.**
> Два механизма, задающих одно и то же число, — второй путь, который §1.3 и §4.2 контракта запрещают.
> Разрешение конфликта — предмет разбора устройства, а не этого документа, но зафиксировать надо здесь:
> **у нас уже есть тот вход, к которому маска подключается, и подключать её надо туда, а не рядом.**
> Симметричность (перераспределяет, а не добавляет) — свойство, которое нарисованная маска обязана
> унаследовать, иначе она сдвинет отображение `Coverage → доля неба`, а его D-20 сделал условием
> переавторизации сцен.

Одно отличие семантики, о котором нельзя умолчать: **у UE маска аддитивна и НЕсимметрична** (положительная
добавляет, отрицательная убирает, среднее по небу двигается), у нас `PatchField` симметричен намеренно.
Это осознанное расхождение, и его надо решить в разборе, а не унаследовать молча.

## 7. Что из этого прямо следует для нашего решения

Три факта, каждый из которых сужает проектное пространство:

1. **У нас уже есть точка, семантически тождественная оси V профиля UE** — `fill` в
   `CloudProceduralVolume.cpp:700`, и её комментарий сам ссылается на D-13. Нарисованный паттерн входит
   туда же, куда входит `Coverage`, и это не новая конструкция, а замена генератора у существующего входа.
2. **У нас уже есть механизм, делающий работу маски** — `PatchField` в той же функции, в тех же строках.
   Два механизма на одно число контракт запрещает, значит нарисованная маска не добавляется рядом, а
   становится **вторым источником того же входа**, с процедурным `PatchField` как источником по умолчанию.
3. **Место, где UE платит за раскладку, у нас уже оплачено другим способом.** Epic читает три текстуры на
   каждом вычислении материала, включая теневые лучи, потому что поля у него нет. У нас поле — испечённый
   том, марш делает **одну выборку** (`CloudField.glslh:270`), и вся раскладка может войти **на стороне
   бейка**, где она стоит ноль в кадре. Это и есть главный результат исследования для проектирования:
   **вопрос «сколько будет стоить чтение текстуры на каждом шаге марша» имеет ответ «нисколько, потому что
   его там не будет»** — при условии, что нарисованный слой сохраняет периодичность тома, чем и
   определяется единственное реальное ограничение конструкции.

Разбор устройства — отдельным сообщением тимлиду, до кода, как требует бриф.

### 8.2. `max` по каналам и неравноправие четвёртого — ПОДТВЕРЖДЕНО, с поправкой к механизму

Подтвердилось:

- Четвёртый вид входит **не в максимум**, а через `LinearInterpolate_12` (узел 126): `A` = `Max_2`,
  `B` = `Multiply` узла 183 (L4143–4144) = `Layout_CloudType.a · TextureSample.a`, `Alpha` =

- У `StormClouds` строки `DefaultValue=` **нет вовсе** (узел 127, L2882–2895). В формате UE отсутствие

  трёхвидовой максимум.

**ПОПРАВКА, и она уточняет `ShapeModel.md` §2.** Тот разбор описывает четыре одинаковые цепочки, чьи
результаты сводятся максимумом. На самом деле максимум берётся по **трём** значениям, и они приходят как

97, L2170–2180). Этот `float3` уже умножен на `Layout_CloudType`, **замаскированный только по RGB** —

То есть **четвёртый вид исключён из максимума структурно, на умножении**, а не «обработан в другом
месте». Для нас разницы в устройстве нет — мы четвёртый слот не выделяем и не собирались, — но описание
эталона становится точным.
