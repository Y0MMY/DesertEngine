# Модель формы `m_SimpleVolumetricCloud` — извлечена из графа

Задача R1. Источник: `../m_SimpleVolumetricCloud.graph.txt` (6555 строк, 298 узлов графа), плюс
скриншоты инстанса и панелей ассетов в `../Inst_params_*.png`, `../textures_*.png`.
Лицензионная рамка: `Docs/Clouds/LICENCE_RECORD.md` — тикет #UE-2026-0842-WAIVER; ограничений на
цитирование значений и порядка операций в нём нет, ограничение одно: бинарные ассеты Epic в дерево не
попадают. Ниже цитируются только числа, имена узлов и связи.

**Каждое утверждение снабжено номером строки в `m_SimpleVolumetricCloud.graph.txt` (`L…`) или именем
узла (`MaterialGraphNode_…`).** Разбор делался парсером (узел → класс выражения → свойства → ссылки
`Expression="…"`), группы восстановлены по геометрии комментарных боксов; скрипты разбора одноразовые
и в дерево не кладутся.

**Главный вывод в одну строку.** Утверждение §2.1 `ANALYSIS_APPROACH.md` («модели формы в UE не
существует как кода — она делегирована ассету») теперь опровергнуто наполовину: **вся модель формы в
графе есть, целиком, и она читается**. Делегированы ассету только четыре таблицы значений (кривые
профилей, паттерн размещения, маска, том шума), и три из четырёх в графе стоят заглушками `Black_1x1`
(L2199, L2314, L2748).

## 0. Как устроен файл и почему модель читается целиком

Материал вычисляется **дважды**, и это несущий факт всей конструкции.

- Узел `VolumetricAdvancedMaterialOutput` (`MaterialGraphNode_13`, L331) получает на вход
  `ConservativeDensity` = `MakeFloat4(…)` (L341, узел `MaterialGraphNode_219` L5024) из четырёх
  именованных реroutes `ConservativeDensity.r/.g/.b/.a` (L4889, L4910, L4965, L5003).
- Узел `VolumetricAdvancedMaterialInput` (`MaterialGraphNode_221`, L5067) **читает эту же величину
  обратно**: его выходной пин `ConservativeDensity as Float4` (L5081) идёт в `BreakOutFloat4Components`
  (`MaterialGraphNode_222`, L5088).
- Корневой пин «Исчезновение» (Extinction, L17 корневого узла) собирается из компонент `.g`, `.b`, `.a`
  этого обратного чтения (L1683, L1806, L1807).

То есть **вся модель формы живёт в вычислении `ConservativeDensity`**, а extinction — тривиальная
рекомбинация уже посчитанного. Поэтому четыре канала `ConservativeDensity` — **не четыре вида облаков**
(предыдущий разбор `MaterialGraph.md` читал их так; это ошибка, см. §12). Это четыре промежуточных
величины:

| Канал | Что это | Узел |
|---|---|---|
| `.r` | консервативная плотность для пропуска пустоты — единственный канал, который читает сам движок | L4889 ← lerp L4358 |
| `.g` | вес по двумерному паттерну размещения | L4910 ← lerp L2946 |
| `.b` | вертикальный профиль, смещённый на −0.5 | L4965 ← subtract L1783 |
| `.a` | шум | L5003 ← static switch `UseNoise3` L5112 |

## 1. Координатный кадр (нужен для всего остального)

`SkyTexScale` (`NamedRerouteDeclaration`, `MaterialGraphNode_46`, L1045) — единая координата, в которой
семплится всё:

```
q           = TruncateLWC( AbsoluteWorldPosition.xyz / KmToCm(Layout_CloudGlobalScale) ) + (0.5, 0.5, 0)
SkyTexScale = float3( Rotate_Z( q.xy, Layout_GlobalTexturePlacement.a ), q.z )
              − Layout_GlobalTexturePlacement.rgb
```

Источники: `WorldPosition` L974 → `Divide` L955 → `Km-to-Cm` L1021 (вход — `Layout_CloudGlobalScale`,
L1026) → `TruncateLWC` L5141 → `Add` L4397 с `Constant3Vector (0.5, 0.5, 0)` L4420 →
`ComponentMask.RG` L4292 → `Rotator` L4268 (`Time` = `Layout_GlobalTexturePlacement.a`, `Speed=1.0`,
L4273–L4274) → `AppendVector` L4339 с `ComponentMask.B` L4316 → `Subtract` L4213.

- `Layout_CloudGlobalScale` = **256.0** км (`ScalarParameter` `MaterialGraphNode_44`, L993; `DefaultValue` L997, `ParameterName` L1000), Desc у `Km-to-Cm` L1032:
  «scaled for clouds at a max height of 8km  maxVisDist = sqrt(h^2+2(6371*h))».
- **Z тоже делится на 256 км.** Это критично для §9: «анизотропия» — это отношение частот в одной и той
  же нормировке, а не отношение тайла к толщине слоя.
- `Layout_GlobalTexturePlacement` (L4232, Desc L4245) — xyz смещение, w поворот вокруг Z.

Ветер, `CloudWind` (`NamedRerouteDeclaration` L805):

```
CloudWind = float4( Layout_WindControls.xyz * Layout_WindControls.a,
                    Time / ( TextureSize(Layout_CloudGlobalPattern).x / Layout_CloudGlobalScale * 1000 ) )
```

Источники: `Layout_WindControls` L545, дефолт **(1.0, 1.0, 0.5, 0.333333)** (L549); `Multiply` L5355;
`Time` с `Period = 9999999` L528/L533; `TextureProperty` L1194 (объект — `Layout_CloudGlobalPattern`,
L1198) → `ComponentMask.R` L1232 → `Divide` на `Layout_CloudGlobalScale` L1213 → `× 1000` L1255 →
`Divide` L1066 → `AppendVector` L851. Смещение октавы = `NoiseN_Coordinates.a · (CloudWind.xyz ·
CloudWind.w)` (`Multiply` L582 — общий множитель, дальше L621, L601, L935).

Замечание: **у ветра есть вертикальная компонента 0.5** (L549), и она делится на масштаб скорости 1/3.

## 2. Группа `Sample Cloud Profiles by Layout Texture` (вопрос A1)

Комментарный бокс: L6281, `Text="Sample Cloud Profiles by Layout Texture"`, позиция (−6400, −768),
размер 3584×1504.

Внутри — **четыре одинаковые цепочки, по одной на вид облака**. Для вида `i ∈ {r, g, b, a}`:

```
uv_i = ( SkyTexScale.xy − 0.5 ) * Layout_CloudPerTypeScale[i]
L_i  = LayoutObject.Sample( uv_i )[i]                       // канал i, паттерн размещения
P_i  = ProfileObject.SampleLevel( float2( NormAltitudeInLayer, L_i ), 0 )[i]   // канал i, профиль
```

Пооперационно, с источниками:

| Шаг | Узлы |
|---|---|
| `SkyTexScale − 0.5` | `Subtract` L1727 (`ConstB=0.5`, L1733) |
| `.xy` | `ComponentMask R,G` L1703 |
| `× PerTypeScale[i]` | `Multiply` L4567 (r), L4586 (g), L4605 (b), L4624 (a) |
| выборка layout | `TextureSample` L4474 (r), L2223 (g), L4505 (b), L4536 (a); объект — `USE LayoutObject` L2929 |
| `Append(NormAltitudeInLayer, L_i)` | `AppendVector` L1897 (r), L1859 (g), L1764 (b), L2842 (a) |
| выборка профиля | `TextureSample` L1916 (r), L1825 (g), L1645 (b), L2808 (a); объект — `USE ProfileObject` L2359; **`MipValueMode = TMVM_MipLevel`, `ConstMipValue = 0`** (L1922–L1924) |

Источник высоты — `CloudSampleAttribute` (`MaterialGraphNode_58`, L1339), пин
**`NormAltitudeInLayer`** (L1354), связанный ровно с четырьмя `AppendVector` (перечислены в самой
строке L1354). Индекс выхода `OutputIndex=2` во всех четырёх ссылках (L1901, L1863, L1768, L2846).

**Выход группы.** Две независимые свёртки по видам:

```
maxLayout  = max( max( L_r·Type_r, L_g·Type_g ), L_b·Type_b )     // L2026, L2045; вход — L2101, L2165
maxProfile = max( max( P_r·Type_r, P_g·Type_g ), P_b·Type_b )     // L1988, L2007; вход — L2120, L2139

ConservativeDensity.r = lerp( maxLayout, max(maxLayout, L_a), StormClouds )      // L4158, L4358
ConservativeDensity.g = lerp( maxLayout, L_a,                StormClouds )      // L2946
ConservativeDensity.b = lerp( maxProfile, P_a·Type_a, StormClouds ) − 0.5       // L2861, L4139, L1783
```

`Layout_CloudType` (`VectorParameter` L2064) — дефолт **(1, 1, 1, 2)** (L2068), т.е. штормовой вид
удвоен. `StormClouds` — скаляр, дефолт 0 (L2882, L2905).

Три детали, которые надо назвать явно:

1. **Правило объединения видов — `max`, а не смешение весами.** Это ровно то правило, которое
   `ANALYSIS_APPROACH.md` §4.3 вывел самостоятельно для двух производителей, и которое
   `PLAN_CLOUD_TYPES.md` T3 предлагает для видов. Оно подтверждено эталоном: L2007, L2045.
2. **Максимум по layout и максимум по профилю берутся НЕЗАВИСИМО** (L2045 против L2007). Победивший в
   одном может не победить в другом. Для нас это ловушка: T3 хочет брать `DetailType` «от вида-
   победителя», и надо решить, от какого именно максимума.
3. **Четвёртый вид (Nimbostratus/Storm) идёт не через max, а через `lerp` по `StormClouds`** (L2861,
   L2946, L4358). То есть буря — не пятый участник максимума, а глобальное переключение режима.

## 3. `ProfileObject` — как устроена текстура профилей (вопрос A2)

**Имя и параметры.** `TextureObjectParameter` `Layout_CloudHeightProfile` (`MaterialGraphNode_102`,
L2306; `ParameterName` L2310, группа `00 - Cloud Layout`, `SortPriority=0` L2312–L2313).
В самом графе там заглушка `Black_1x1_EXR_Texture` (L2314). Реальная текстура видна в инстансе:

- `Inst_params_1.png`: `Layout_CloudHeightProfile = T_Profile_08`.
- `textures_3.png` (инфо-панель ассета): `T_Profile_08`, Texture2D, **256 × 256**, формат
  **FloatRGBA**, Compression `HDR`, sRGB **False**, альфа есть, исходный формат `TSF RGBA16F`, ≈202 КиБ на диске, путь `/Engine/EngineSky/VolumetricClouds`, Wrap по обеим осям.

**Как устроена.** Это **двумерная таблица**, а не набор кривых по одной оси:

- **U (горизонталь) = `NormAltitudeInLayer`**, доля слоя 0…1 — первый аргумент `AppendVector`
  (L1901/L1863/L1768/L2846).
- **V (вертикаль) = значение layout-текстуры `L_i` в этой точке неба** — второй аргумент
  (L1902/L1864/L1769/L2847), причём это **тот же самый канал того же семпла**, который потом станет
  множителем `ConservativeDensity.g`.
- **Канал = вид облака.** Из выборки берётся ровно тот канал, что и у layout: R для r-цепочки (L1944),
  G (L1854), B (L1675), A (L2839).

Каналы названы в Desc параметра, L2320: «*This texture describes the shape of the clouds as the altitue
[sic] changes. Each channel of this texture describes the profile shape **and relative altitude** of a
different cloud type ( r = stratocumulus, g = altostratus, and b = cirrostratus, a = nimbostratus )*».
Те же имена продублированы как `ChannelNames`/`Outputs` у `Layout_CloudPerTypeScale` (L4442, L4454–L4457).

**Из этого следует главное:** вертикальный профиль вида — не кривая `f(h)`, а **семейство кривых
`f(h, coverage)`**. При слабом паттерне вид получает одну кривую, при сильном — другую: другую высоту
основания, другую толщину, другую форму. Одна текстура даёт и «где облако» → «какой оно высоты», без
единого дополнительного параметра и без шума.

Ещё: выборка принудительно с мипа 0 (L1922–L1924). Мипы профиля запрещены — иначе вдали кривые
разных coverage смешиваются между собой, и вид теряет форму.

## 4. `LayoutObject` и `Layout_CloudGlobalScale` (вопрос A3)

**Имя и параметры.** `TextureObjectParameter` `Layout_CloudGlobalPattern` (`MaterialGraphNode_98`,
L2191; `ParameterName` L2195; заглушка `Black_1x1` L2199). Desc, L2205: «*This texture defines the
world location for each type of cloud where each channel describes a different cloud type ( r =
stratocumulus, g = altostratus, and b = cirrostratus, a = nimbostratus )*». В инстансе —
`T_ColorGrid` (`Inst_params_1.png`).

**Ответ на вопрос «разбиение неба по видам, смешение весами, или что-то третье»: третье.**
Каждый канал — **независимое двумерное поле присутствия своего вида**, со своим масштабом
(`Layout_CloudPerTypeScale`, L4437, дефолт (1,1,1,1), L4441) и своим множителем видимости
(`Layout_CloudType`, L2064, дефолт (1,1,1,2)). Ни нормировки суммы весов, ни smoothstep-разбиения, ни
lerp между видами в графе **нет**. Виды имеют право перекрываться; конфликт разрешается максимумом
(L2007, L2045) в самом конце.

`Layout_CloudGlobalScale = 256` км (L997) — **период повторения layout-текстуры по миру**, через
нормировку `worldPos / KmToCm(256)` (L955, L1021). Он же служит нормировкой для координат всех трёх
октав шума (§10) и для скорости ветра (L1213–L1255).

Значение `L_i` используется **дважды и по-разному**:
1. как V-координата в текстуру профилей (§3) — решает, *какой формы* здесь облако;
2. как внешний множитель `ConservativeDensity.g` (L2946) — решает, *есть ли* здесь облако.

## 5. `MaskObject` / `Apply Mask Texture` (вопрос A4)

Комментарный бокс L6406, позиция (−2560, −768), размер 1408×640.

```
maskUV   = ( SkyTexScale + Layout_GlobalTexturePlacement.rgb ).xy      // Add L4792 → Mask.RG L2549
M        = MaskObject.Sample( maskUV ).rgb                             // TextureSample L2590
maskTerm = dot( Layout_CloudTypeMask.rgb, M · Layout_CloudType.rgb )
           · ( Layout_CloudTypeMask.a · 0.01 )                         // Multiply L2621, Dot L5971,
                                                                       // Multiply L2720 (ConstB=0.010000, L2726), L2678
```

- `Layout_GlobalCloudMask` — `TextureObjectParameter` L2740 (`ParameterName` L2744, заглушка L2748),
  Desc L2754: «*can be used to add clouds to or remove clouds from the global pattern texture in the
  masked region… The alpha channel is unused*». В инстансе — `T_CloudMask` (`Inst_params_1.png`).
- `Layout_CloudTypeMask` — `VectorParameter` L4828, дефолт **(0, 0, 0, 1)** (L4832), т.е. **по
  умолчанию маска даёт ровно ноль**. Альфа — общий вклад маски, и она дополнительно давится на 0.01
  (L2726).
- Обратите внимание на координату: `SkyTexScale` уже вычел `Layout_GlobalTexturePlacement.rgb`
  (L4213), а здесь он прибавлен обратно (L4792). **Маска привязана к миру и не двигается смещением
  паттерна.**

**Порядок относительно покрытия — маска аддитивна и стоит ПОСЛЕ всего остального.** Она не входит ни в
профиль, ни в шум, ни в покрытие: она складывается с уже собранной формой (`Add`,
`MaterialGraphNode_121`, L2697, **с авторским комментарием `Desc="Add additive mask"`, L2707**), и
только потом всё умножается на глобальную плотность. Вычитать маска умеет за счёт отрицательных
значений `Layout_CloudTypeMask`, а не за счёт умножения.

## 6. `Global Coverage Control` (вопрос A5)

Комментарный бокс L6306 содержит **ровно один узел** — `ScalarParameter` `Cloud_GlobalCoverage`
(`MaterialGraphNode_71`, L1579), дефолт **−0.2** (L1583), `ParameterName` L1586, группа `00 - Cloud Layout` (L1588),
`SortPriority=100` (L1589), Desc L1594. Подтверждение в инстансе: `Inst_params_2.png`, `Cloud_GlobalCoverage
= −0,2`.

У параметра **два потребителя** и оба — сложение внутри шумового члена:

```
ConservativeDensity.a (UseNoise3 = false, дефолт) :
    ( Noise1.g − Noise_Bias.r + Cloud_GlobalCoverage ) · Noise_Strength.r          // L292, L1607, L312

третья октава (UseNoise3 = true) :
    … + Noise_Strength.b · ( Cloud_GlobalCoverage + Noise3.b − Noise_Bias.b )      // L711, L1626, L731
```

**Точная композиция, буквально:**

```
shape = ConservativeDensity.g · ( ConservativeDensity.b + ConservativeDensity.a )
      = layoutWeight · ( (profile − 0.5) + (noise − bias + coverage) · strength )
```

Источники: `Multiply` L1679 с авторским комментарием **`Desc="Weight By 2d Cloud Texture"` (L1690)**,
`Add` L1802 с комментарием **`Desc="Blend Profiles + Volume Noise"` (L1812)**.

Отвечая на вопрос дословно:

- покрытие входит **сложением**, не умножением, и **не имеет клампа** — это чистый биас;
- покрытие применяется **к шуму**, до сложения с профилем;
- **профиль и шум складываются**, а не перемножаются и не ремапятся;
- **двумерное поле размещения — единственный множитель**, и он снаружи всей суммы;
- смещение `−0.5` у профиля (L1783/L1788) делает профиль **знакопеременным**: там, где профиль ниже
  половины, он *вычитает* из шума, то есть работает как порог, а не как огибающая.

## 7. Полная формула extinction

Собрано целиком, каждая строка со своим узлом:

```
h        = NormAltitudeInLayer                                     // CloudSampleAttribute L1339 / L432 / L1417

shape    = CD.g · ( CD.b + CD.a )                                  // L1679 "Weight By 2d Cloud Texture"
                                                                   // L1802 "Blend Profiles + Volume Noise"
sum      = maskTerm + shape                                        // L2697 "Add additive mask"
density  = sum · lerp( Cloud_GlobalDensity,
                       Cloud_GlobalDensity + 0.666667·StormClouds,
                       StormClouds )                               // L2499 "Global Density", lerp L3817, L5878, L5897
faded    = density · saturate( length(CameraRelativeWorldPosition) · 0.00002 )   // L240, L769, L786, L5318, L5338
gate     = ( |h − 0.5| ≤ 0.48 ) ? 1 : 0                            // If L450, EqualsThreshold=0.48 L459
Extinction = saturate( gate · faded )                              // Multiply L2480, Saturate L165, корень L17
```

`Cloud_GlobalDensity` = **0.008** (`ScalarParameter` L2522, дефолт L2526).
Альбедо: `lerp( Cloud_AlbedoColor, Storm_AlbedoColor, … )` — `Cloud_AlbedoColor` = (0.98, 0.98, 0.98,
0.5) L203/L207, `Storm_AlbedoColor` = (0.3, 0.3375, 0.375, 0.333333) L3683/L3687, lerp L125.
`Phase_Controls` = (0.8, 0.166667, 0.575, 1.0) L5219/L5223; `Multiscatter_Controls` = (0.666667, 0.25,
0.18, 1.0) L5182/L5186; `MultiScatteringApproximationOctaveCount = 2` (L342). Это подтверждает числа,
уже принятые в `MaterialGraph.md`.

## 8. `Fade Near Camera` (вопрос B6)

Комментарный бокс L6331, позиция (−128, 384), размер 768×256. В нём **четыре узла**, и это вся техника:

| Узел | Строка | Что делает |
|---|---|---|
| `WorldPosition` | L5318 | `WorldPositionShaderOffset = WPT_CameraRelative` (L5322) |
| `Length` | L5338 | длина вектора |
| `Multiply` | L786 | `ConstB = 0.00002` (L791) |
| `Saturate` | L769 | зажим в 0…1 |

```
fade = saturate( length( CameraRelativeWorldPosition ) · 0.00002 )
```

Умножается на плотность в `Multiply` L240 (пины L255/L256), то есть **до** высотного гейта и до
финального `saturate`.

Числа: UE меряет в сантиметрах, `1 / 0.00002 = 50 000 см = **500 м**`. Линейный подъём от 0 у камеры
до 1 на 500 метрах. Никакого smoothstep, никакого параметра — константа зашита в граф.

## 9. `Prevent Shadowing from Above Clouds` (вопрос B7)

Комментарный бокс L6156, позиция (256, −320), размер 512×448. В нём **пять узлов**:

| Узел | Строка | Значение |
|---|---|---|
| `CloudSampleAttribute` | L432 | используется пин `NormAltitudeInLayer` (L447), `OutputIndex=2` (L454) |
| `If` | L450 | `EqualsThreshold = 0.480000` (L459) |
| `Constant` | L478 | `R = 0.5` — вход `B` |
| `Constant` | L495 | `R = 1.0` — ветка `A == B` |
| `Constant` | L512 | `0` — обе ветки `A > B` и `A < B` (L456, L458) |

```
gate = ( abs( NormAltitudeInLayer − 0.5 ) ≤ 0.48 ) ? 1.0 : 0.0
     = ( NormAltitudeInLayer ∈ [0.02, 0.98] ) ? 1.0 : 0.0
```

**Какой вход правит:** результат — множитель самой `Extinction`, узел `Multiply` L2480 (пин `A` —
L2495), сразу перед корневым `Saturate` L165. То есть **вырезается плотность в нижних 2 % и верхних
2 % толщины слоя**.

Почему это названо «prevent shadowing from above clouds» — **в графе не объяснено**; сам механизм
однозначен. Правдоподобное чтение (помечаю как чтение, не как факт): текстура профилей — авторские
данные с Wrap-сэмплированием, и ничто не гарантирует, что кривая приходит в нуль на границах слоя.
Облако, дотягивающееся до потолка слоя, затеняет собой всё, что под ним, и небо получает крышку;
двухпроцентная отсечка гарантирует, что верх и низ слоя пусты. Это в точности тот дефект, который
программа уже ловила на своей стороне («небо было потолком», коммит `54330ab9`).

## 10. Шумовой стек (вопрос C10)

Два вектора параметров, и **предыдущий разбор их перепутал** (см. §12):

| Параметр | Узел | Дефолт | Имена каналов |

| `Noise_Bias` | L5478 | **(0.5, 0.8, 0.5, 0.0)** (L5482) | Noise1 / Noise2 / Noise3 / N/A (L5483) |
| `Noise_Strength` | L5515 | **(0.8, 0.08, 0.03, 2.5)** (L5519) | Noise1 / Noise2 / Noise3 / StormyDistortFactor (L5520) |

Desc `Noise_Bias`, L5492: «*Each parameter in this set is subtracted [from] the respective NoiseTexture
sample… This determines how the noise texture dilates or erodes the Cloud Layout **without increasing
the overall contrast** of the noise*». Desc `Noise_Strength`, L5529: «*multiplied against the respective

такие: bias двигает порог, strength двигает контраст.

Координаты октав (все — `NoiseN_Coordinates.xyz · SkyTexScale + NoiseN_Coordinates.a · wind`):

| Параметр | Узел | Дефолт | Канал тома | Период по миру (X / Y / Z) |
|---|---|---|---|---|
| `Noise1_Coordinates` | L1157 | (4.167, 4.444, **9.091**, **+7.0**) (L1161) | **G** (Desc L1171) | 61.4 / 57.6 / **28.2** км |
| `Noise2_Coordinates` | L1083 | (60, 60, **75**, **−6.0**) (L1087) | **R** (Desc L1097) | 4.27 / 4.27 / 3.41 км |
| `Noise3_Coordinates` | L1120 | (30, 40, 25, +8.0) (L1124) | **B** (Desc L1134) | 8.53 / 6.40 / 10.24 км |

Каналы тома подтверждаются связями: `.G` берётся у выборки Noise1 (L296), `.R` у Noise2 (L397), `.B` у
Noise3 (L711); и Desc тома, L2267: «*r = Noise1, g = Noise2, and b = Noise3… alpha channel which is
unused*» — **имена в Desc тома переставлены относительно фактических связей и относительно Desc самих
`NoiseN_Coordinates`**; фактические связи (L296/L397/L711) и Desc параметров (L1171 «green channel»,
L1097 «red channel», L1134 «blue channel») согласуются между собой, а Desc тома — нет. Верим связям.

**Как ТОЧНО складываются три октавы.** Ответ: **никакого remap нет ни в одном месте.** Октавы 1 и 3
складываются, октава 2 не складывается вообще — она **искажает координаты** первой:

```
t   = 0.05 + 0.95 · NormAltitudeInLayer                            // L1524 (×(1−0.05) L1543/L1435), L1560
D   = float3( t, t, (2·|t − 0.5|)² )                               // MakeFloat3 L1393; L2444 abs, L2461 ×2, L1878 квадрат
w2  = ( Noise2.r − Noise_Bias.g ) · lerp( Noise_Strength.g,
                                          Noise_Strength.g · Noise_Strength.a,
                                          StormClouds )            // L393, L413, L3662, L3864
coords1 = Noise1_Coordinates.xyz · SkyTexScale
        + Noise1_Coordinates.a · wind
        + D · w2                                                    // L1469, L621, L1374, L1297
N1  = Noise3D( coords1 ).g                                          // L259, L296
CD.a = ( N1 − Noise_Bias.r + Cloud_GlobalCoverage ) · Noise_Strength.r      // L292, L1607, L312
```

При `UseNoise3 = true` (`StaticSwitchParameter` L5112, дефолт **false**, L5138) добавляется третья
октава, входящая **и мультипликативно, и аддитивно**:

```
M    = lerp( dot(Noise3_MultChannel.rgb, N3.rgb), N3.g, StormClouds ) · Noise3_MultChannel.a   // L3884, L5374, L5393
CD.a = CD.a_base · M + Noise_Strength.b · ( Cloud_GlobalCoverage + N3.b − Noise_Bias.b )       // L1316, L1274, L731
```

`Noise3_MultChannel` = (0, 0, 1, 0.4) (L5397), т.е. по умолчанию `M = N3.b · 0.4`.

**Домен-варп `D` — самая важная находка этого раздела.** Горизонтальная часть искажения растёт линейно
с высотой в слое (от 0.05 у основания до 1.0 у верхушки), вертикальная — парабола, равная нулю в
середине слоя и максимальная на обоих концах. Это и есть механизм, которым UE ломает вертикальную
экструзию: **один и тот же двумерный паттерн даёт разный силуэт на разной высоте**. У нас такого нет
вообще ни в каком виде.

Разнонаправленный ветер (+7 у Noise1 против −6 у Noise2, L1161/L1087) — подтверждён, читается как
раньше.

## 11. Проверка наших решений

### 11.1. Профиль: выражает ли текстура то, чего не выражает параметрика (вопрос C8)

**Да, и в двух независимых смыслах.**

Наш `CloudVerticalProfile( heightFraction, cloudType )` (`Editor/Resources/Shaders/Common/CloudField.glslh:80`)
— одна кривая `f(h)` с двумя числами: `topEnd = mix(0.06, 0.35, type)` (строка 89), `baseEnd =
mix(0.01, 0.05, type)` (строка 90), рампа снизу и рампа сверху (строки 92–95). План T0 хочет заменить
это на `BaseAltitudeKm, TopAltitudeKm, BaseSharpness, TopTaper` — это по-прежнему **одна кривая `f(h)`**,
просто с четырьмя числами вместо двух.

Чего одна кривая `f(h)` не выражает:

1. **Зависимости формы от покрытия.** У UE профиль — `P(h, L)`, где `L` — локальное значение
   двумерного паттерна (L1901–L1902). Пример, который параметрика не даёт: у края пятна покрытия
   (`L ≈ 0.2`) вид получает низкую плоскую кривую — плоское, тонкое, невысокое облако; в центре пятна
   (`L ≈ 0.9`) тот же вид получает высокую кривую — башню. **Один вид, одна текстура, ноль
   дополнительных параметров, и башни стоят там, где облака гуще, а не там, где повезло шуму.**
   В нашей конструкции высота вида одинакова по всему небу, и единственный способ её разнообразить —
   `CloudTypeVariance` (`CloudField.glslh:145–146`), т.е. подмешать шум в *тип*. Это не то же самое:
   шум не коррелирован с покрытием, поэтому башня может вырасти на разрежённом краю.
2. **Произвольной формы кривой.** Текстура даёт многомодальные профили. Пример, который прямо стоит в
   каталоге форм (`ANALYSIS_APPROACH.md` §6): **кумулонимбус с наковальней** — узкая колонна плюс
   расширение у самого верха. Это кривая с двумя горбами; произведение `baseRamp · topRamp` (наши
   строки 92–95) её не порождает ни при каких четырёх числах.

И третье, из Desc L2320: канал кодирует «*profile shape **and relative altitude***» — то есть у UE
даже «на какой высоте живёт вид» это **данные внутри кривой**, а не отдельный параметр.

**Что это НЕ отменяет.** Абсолютный якорь высоты (правило §5.1 анализа, решение T0 «высоты —
абсолютные») — про другое: он про то, что нельзя описывать вид одними отношениями. Кривая-как-данные и
абсолютный якорь совместимы: якорь становится метаданными кривой (её домен в километрах), а не заменой
кривой.

### 11.2. Анизотропия 2.2 (вопрос C9)

Наше число: `verticalTile = tile / 2.2` (`CloudField.glslh:130`), выведено из 9.091/4.167 = 2.18.

По графу (L1161, L1087, L1124):

| Октава | Z/X | Z/Y | **Y/X (горизонтальная)** |
|---|---|---|---|
| Noise1 | 9.091/4.167 = **2.182** | 9.091/4.444 = **2.046** | 4.444/4.167 = **1.0665** |
| Noise2 | 75/60 = **1.25** | 1.25 | 60/60 = **1.0** |
| Noise3 | 25/30 = **0.833** | 25/40 = **0.625** | 40/30 = **1.333** |

**Да, горизонтальная анизотропия в графе есть, и мы её потеряли**: у первой октавы поле растянуто по X
относительно Y на **6.65 %**. Это немного, но потеряно и кое-что большее:

- **вертикальная анизотропия у нас одна на всё поле, а в графе она своя у каждой октавы** — 2.18 у
  базовой, 1.25 у искажающей, **0.83 у третьей**;
- **у третьей октавы анизотропия обратная** (Z/X < 1): она растянута по вертикали, а не сжата. То есть
  UE намеренно делает грубую форму приплюснутой, а мелкую деталь — вытянутой вверх. Одним скаляром
  такое не описывается в принципе;
- наша анизотропия применена только к оси Y при выборке покрытия (`CloudField.glslh:130–132`) и **не
  применена вообще** к выборке детали (`CloudField.glslh:216–217`, изотропный `detailPos`). В графе
  анизотропия есть у всех трёх октав.

### 11.3. Композиция плотности

Наш `CloudSampleDensity` (`CloudField.glslh:208–240`): `CloudRemap( Profile, erosion, 1, 0, 1 )` с
`erosion = detail · strength · (1 − Profile)`.

В графе `CloudRemap`-подобной конструкции **нет ни в одном месте**. Есть только:
`layout · ( (profile − 0.5) + (noise − bias + coverage) · strength )` (L1679, L1802).

Это не значит, что мы обязаны переписаться под UE: решение D-1 говорит «Nubis решает данные, форму и
затенение», а remap-эрозия взята из доклада (сл. 120, `ValueErosion`). Но это значит, что **наш
smoothstep-порог покрытия (`CloudField.glslh:178–186`) не имеет эталона ни у UE, ни у Nubis** — он наш
собственный, и в журнале решений его нет. Это надо либо обосновать, либо заменить на биас (UE) или на
remap (Nubis).

## 14. Что это меняет в плане T

Это главный продукт задачи. Ниже — пункты `PLAN_CLOUD_TYPES.md`, которые надо переписать, и как.

### T0 — переписать модель `CloudShapeParams`

**T0.1. Профиль перестаёт быть кривой и становится семейством кривых.** Список параметров T0
(`PLAN_CLOUD_TYPES.md` §2, блок `CloudShapeParams`) сейчас описывает `f(h)`: `BaseAltitudeKm,
TopAltitudeKm, BaseSharpness, TopTaper`. Заменить на `f(h, coverage)`, потому что иначе высота вида
одинакова по всему небу (§11.1). Два варианта, оба совместимы с деревом:

- *ресурсный*: 1D/2D-LUT, испечённый из параметров вида (UE: 256×256 RGBA16F — у нас 2D-текстуры с
  мипами есть, ограничение §2.3 анализа касается только 3D);
- *параметрический*: `BaseAltitudeKm`, `TopAltitudeKm` становятся функциями локального покрытия —
  минимум `TopAltitudeKm = mix(TopAltitudeKm_min, TopAltitudeKm_max, coverageLocal)`.

Второй дешевле и решает пункт 1 из §11.1; первый решает ещё и пункт 2 (наковальня). **Рекомендация
тимлиду: делать параметрический вариант в T0, а LUT — в T1 вместе с ассетом**, потому что кривая как
данные и есть содержимое ассета.
**Тест на отношение (новый, в сюиту `CloudField`):** интеграл профиля при `coverage = 0.2` строго
меньше, чем при `coverage = 0.9`. Без него первый пункт T0 не проверяем.

**T0.2. Абсолютные высоты остаются, формулировка уточняется.** Решение «высоты вида абсолютные» не
отменяется (у UE вертикальный вход — доля слоя, но «relative altitude» вида зашита в кривую, L2320,
что эквивалентно). Уточнение: **абсолютная высота — это домен кривой, а не замена кривой.**

**T0.3. `Anisotropy` — не скаляр, а вектор на октаву.** Пункт «`Anisotropy` — отношение горизонтальной
частоты к вертикальной» переписать на три тайла (X, Y, Z) **отдельно для поля покрытия и для поля
детали**. Стартовые числа взять из графа: покрытие (4.167, 4.444, 9.091), деталь (60, 60, 75) —
в нормировке 256 км это периоды 61.4/57.6/28.2 км и 4.27/4.27/3.41 км. Заодно исправляется дефект:
сегодня `detailPos` изотропен (`CloudField.glslh:216–217`).

**T0.4. Добавить домен-варп по высоте — этого нет вообще.** Новый пункт в T0, из §10:
координаты поля покрытия смещаются вторым шумом на вектор `float3(t, t, (2|t−0.5|)²) · (n₂ − bias) ·
strength`, `t = 0.05 + 0.95·h`. Это стоит одну уже существующую выборку (`CLOUD_SAMPLE_NOISE` и так
возвращает четыре канала) и напрямую бьёт по тому дефекту, ради которого писан комментарий в
`CloudField.glslh:100–115`. **Это, а не профиль, — механизм, которым UE делает силуэт трёхмерным.**

**T0.5. Записать в журнал решений расхождение по композиции.** Наш `smoothstep`-порог покрытия
(`CloudField.glslh:178–186`) и наш `CloudRemap`-эрозия — не из UE (§11.3). У UE покрытие — аддитивный
биас без клампа, профиль складывается с шумом со смещением −0.5, и единственное умножение — на
двумерное поле. Правило §5.5 анализа («отказ и решение записываются вместе со своим несущим входом»)
требует это зафиксировать: либо мы принимаем конструкцию Nubis и называем её, либо чиним.

**T0.6. Две однострочные техники — забрать сразу, они дешевле теста на них.**
`fade = saturate(dist · 0.00002)` (500 м) и `gate = |h − 0.5| ≤ 0.48`. Обе — множители extinction.

### T1 — ассет «Тип облака» меняет содержимое

**T1.1. Ассет несёт кривую, а не только скаляры.** Из T0.1: если форма — семейство кривых, то ассет
обязан хранить кривую (набор контрольных точек + испечённый LUT), иначе «загрузить свой вид» сводится
к перестановке четырёх чисел. Это ровно то, что просил владелец («текстуры… чтобы были свои виды»).

**T1.2. Каталог видов: назвать расхождение с Epic.** У Epic виды — **четыре канала одной пары
текстур** (L2320, L2205), причём три из четырёх слоистые: Stratocumulus / Altostratus / Cirrostratus /
Nimbostratus. Наш план — девять независимых ассетов. Это осознанное расхождение, и его надо записать:
канальная схема ограничена четырьмя видами, но даёт бесплатное сосуществование видов в одном небе
(см. T3.1); схема «ассет на вид» не ограничена числом, но требует отдельного механизма сосуществования.

**T1.3. Два параметра, которых нет ни у нас, ни в плане:** видимость на вид (`Layout_CloudType`, L2064,
дефолт (1,1,1,2)) и масштаб паттерна на вид (`Layout_CloudPerTypeScale`, L4437). Первый — это «выключи
цирростратус в этой сцене», второй — «сделай пятна кучёвки мельче, чем пятна слоистых». Оба дешёвые.

### T3 — правило смешения: половина подтвердилась, половина переписывается

**T3.1. `max` подтверждён — можно ссылаться на эталон.** «`Profile = max по видам (weight_i ×
profile_i)`» — ровно то, что делает граф (`Max` L1988, L2007; веса — `Layout_CloudType`, L2120). Пункт
остаётся, к нему добавляется ссылка.

**T3.2. Веса — НЕ разбиение одного поля.** Пункт T3 «веса — разбиение поля типа `smoothstep`'ом с узкой
полосой перехода» противоречит эталону и его надо переписать. У UE вес каждого вида — **независимое
двумерное поле** (свой канал текстуры, свой масштаб; L2205, L4437). Разница содержательная, а не
стилистическая: разбиение запрещает видам перекрываться и заставляет их иметь один и тот же размер
пятен, независимые поля — нет. Пример, который разбиение не даёт: сплошная пелена altostratus по всему
небу, **сквозь которую** местами пробивают башни congestus. Это ровно кадр из ⬛ ПОКАЗ T3.

**T3.3. Решить, от какого максимума брать `DetailType`.** У UE максимум по полю размещения и максимум
по профилю берутся независимо (L2045 против L2007), и победители могут отличаться. Наш план говорит
«от вида-победителя», не уточняя, какого. Уточнить в тексте плана — иначе это молчаливое решение в коде.

**T3.4. Буря — не пятый вид, а режим.** У Epic четвёртый вид входит через `lerp` по `StormClouds`
(L2861, L2946, L4358), а не в максимум. Если мы возьмём девять равноправных видов, то у нас нет
эквивалента этого переключателя; стоит решить сознательно, а не обнаружить.

### T2 — подтверждения, менять нечего

Размер тома шума в T2 (128³ RGBA) **совпадает с эталоном**: `T_Volume_PerlinWorley_Balanced` 2048×1024
= 128³ (`textures_2.png`). Смысл каналов у UE — три октавы одного и того же Perlin-Worley с разными
масштабами (L2267 и связи L296/L397/L711), а не четыре разных шума; наш план берёт схему Nubis
(Curly-Alligator/Alligator), что богаче. Расхождение осознанное, менять не надо.
